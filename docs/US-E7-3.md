# US-E7-3 — Report export (CSP-253)

A Company Admin or Area Manager exports a dashboard report, and a Company Admin exports a filtered audit extract, to CSV or PDF. The file is generated in the background and downloaded from a link. It follows the same role scoping as the screens.

## Job model and endpoints (BE1, CSP-525)
Table `reporting.report_export` (migration `20261015090000_ReportExports`, hand-written SQL in `SchemaSql.cs`): requester `sub`, name and role, the **scope snapshot** `scope_province_ids` (null = company-wide), report type, filters (`jsonb`), format, status, `created_at` / `started_at` / `completed_at` / `expires_at`, file name, content type, `content` (`bytea`) and a short `error`. Files are kept in the database because there is no blob storage and exports are small. `audit_app` already has DML on the `reporting` schema; re-running `scripts/create-db-roles.sql` after the migration covers the new table.

| Route | Roles | Answer |
|---|---|---|
| `POST /api/reports/export` `{ reportType, format, filters }` | CompanyAdmin, AreaManager | `202 { "exportId" }` at once; `400` invalid; `403` audit extract by a non-admin; `503` if Organization is down for an Area Manager |
| `GET /api/reports/export` | same | the caller's latest 20 exports, newest first, without content |
| `GET /api/reports/export/{id}` | same | status and times; `downloadPath` when `Ready` |
| `GET /api/reports/export/{id}/file` | same | the file; `404` for anyone but the requester, `409` not ready, `410` expired or removed |

- `reportType`: `sales-summary`, `sales-breakdown`, `audit-extract`. `format`: `csv` or `pdf`.
- Filters for `sales-summary`: `from`, `to`, `compareFrom`, `compareTo`. For `sales-breakdown`: `from`, `to`, `groupBy`, `sort`, `direction`. They are validated with the on-screen rules (`from` ≤ `to`, at most 1,100 days, compare dates given together).
- Filters for `audit-extract`: `aggregateType`, `aggregateId`, `orderReference`, `actorUserId`, `eventType`, `occurredFrom`, `occurredTo`. These are the `GET /api/audit` filters; its `from`/`to` are named `occurredFrom`/`occurredTo` here because `from`/`to` are dates for the sales reports.
- Only the filters a report type uses are stored, with the on-screen defaults applied (`sort=value`, `direction=desc`).
- **Scoping rule**: the requester, role, company and provinces are taken from the caller's token (provinces from Organization `/api/me/scope`, as on screen) when the job is submitted, never from the body. Status, file and list are filtered by company **and** `sub`, so another user gets `404` and cannot tell whether the id exists.
- The download sets `Content-Type`, `Cache-Control: no-store` and a `Content-Disposition` file name with only letters, digits, `-`, `_` and `.`. CORS exposes `Content-Disposition` so the web app can read the name.

Statuses: `Queued` → `Running` → `Ready` or `Failed`; `Ready` → `Expired`. A `Ready` export past `expiresAt` reads as `Expired` even before the cleanup runs.

## Background generator (BE2, CSP-526)
- A hosted worker polls every `Exports:PollSeconds` (5). In one transaction it claims the oldest `Queued` job with `SELECT … FOR UPDATE SKIP LOCKED` and sets it `Running`, so two workers or instances never claim the same job. It builds the file, then sets `Ready` with `expiresAt = completedAt + Exports:ExpiryHours` (24). If the job throws, it is set `Failed` with a short fixed message, the details go to the log, and the worker carries on.
- The worker has no token. It runs **the same query services as the screens** (`IReportQueryService`, `IAuditReadService`) with the stored scope snapshot, so the file has the rows and figures the screen shows for the same filters.
- Territory names: the worker cannot call Organization without a token. It uses the names already stored on the territory dimension (saved when a user viewed the breakdown), and short IDs otherwise. The screen shows the same short IDs when Organization is down.
- Audit extracts are read in pages of 1,000 with keyset paging, in the on-screen order, and are capped at 50,000 rows. The header says when the cap was reached.
- Both formats start with a header block: report title, generated by (requester name), generated at (UTC), the filters and the scope (`Company-wide` or the province ids). Then the table.
- **CSV**: RFC 4180 (fields with a comma, quote or line break are quoted, quotes doubled), CRLF, UTF-8 **with BOM** so Excel shows Sinhala and Tamil. A text cell starting with `=`, `+`, `-`, `@`, tab or CR gets a leading `'` so a spreadsheet does not run it as a formula. Numbers are written as plain numbers.
- **PDF**: QuestPDF (Community licence, set once at startup), landscape A4 table with page numbers.

## Expiry cleanup (BE3, CSP-527)
Every `Exports:CleanupMinutes` (60), `Ready` exports past `expiresAt` get `content = NULL` and status `Expired`. The row stays, so "My exports" can show it as expired.

## Known limits
- The PDF uses QuestPDF's default fonts, which may not render Sinhala or Tamil glyphs. Use CSV for those names.
- A job that is `Running` when its instance stops stays `Running`; it is never picked up again, so it can never be built twice. Export the report again.
- Files are held in memory while they are built; audit extracts are capped at 50,000 rows for that reason.
- The runtime image needs `libfontconfig1` for QuestPDF; the Dockerfile already installs it.
